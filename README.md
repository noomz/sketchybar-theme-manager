# stm — SketchyBar Theme Manager

Switch [SketchyBar](https://github.com/FelixKratz/SketchyBar) colour themes with one command.

```console
$ stm apply catppuccin-mocha
Applied Catppuccin Mocha (catppuccin-mocha) -> ~/.config/sketchybar/colors_generated.lua
```

SketchyBar has no standard way to change colours. Everyone ends up hand-editing
`colors.lua` or `colors.sh`, keeping half-finished palettes in comments, or
writing a one-off script in their dotfiles. `stm` makes the palette a data file
and the switch a command.

It is a single bash script. No Node, no Python, no Lua, no package manager, no
runtime of any kind — just the tools already on a stock macOS install.

---

## Install

**One-liner**

```sh
curl -fsSL https://raw.githubusercontent.com/noomz/sketchybar-theme-manager/main/install.sh | sh
```

Installs to `~/.local` by default (`STM_PREFIX` to change it). It never uses
`sudo`, and it never edits your shell rc files — it just prints the `PATH` line
if you need one.

**Homebrew**

```sh
brew install noomz/tap/sketchybar-theme-manager
```

Or straight from a checkout, no tap required:

```sh
brew install --formula ./Formula/sketchybar-theme-manager.rb
```

**Manual**

```sh
git clone https://github.com/noomz/sketchybar-theme-manager.git
cd sketchybar-theme-manager
ln -s "$PWD/bin/stm" ~/.local/bin/stm
```

The script finds its bundled palettes relative to its own location, so a
symlink works fine.

## Quick start

```sh
stm list                      # what's available
stm preview nord              # look before you leap
stm apply nord                # write it and reload SketchyBar
stm current                   # nord
```

## Commands

| Command | What it does |
| --- | --- |
| `stm list` | List available themes; `*` marks the active one |
| `stm apply <theme>` | Apply a theme, then run `sketchybar --reload` |
| `stm current` | Print the active theme slug |
| `stm init [--format lua\|bash]` | Scaffold `./palettes` and `./stm.config.toml` |
| `stm add <theme> <palette-file>` | Install a palette into your palette directory |
| `stm preview <theme>` | Print a theme's colour table — writes nothing |
| `stm doctor [theme]` | Diagnose the config: format, dialect, key coverage |
| `stm verify` | Check that stm touched only the files it owns |
| `stm import [<file>]` | Turn an existing colours file into a palette |
| `stm export <theme>` | Print a theme as canonical palette TOML |
| `stm help` | Show usage |
| `stm version` | Print the version |

## Options

| Option | Meaning |
| --- | --- |
| `--dir <path>` | SketchyBar config dir (overrides `$SKETCHYBAR_CONFIG_DIR`) |
| `--palette-dir <path>` | Palette directory to search |
| `--config <path>` | Path to `stm.config.toml` |
| `--format <f>` | Force `lua`, `bash` or `config-sh` instead of auto-detecting |
| `--lua-dialect <d>` | `flat`, `nested` or `auto` (default: auto-detect) |
| `--no-manifest` | Don't record a checksum baseline on apply |
| `--backup-each` | Keep a timestamped backup before each destructive write |
| `--out <file>` | Write `export` output to a file |
| `--slug <slug>` | Name for the palette `import` creates |
| `--base <slug>` | Make the imported palette inherit from `<slug>` |
| `--no-reload` | Don't run `sketchybar --reload` after applying |
| `--dry-run` | Show what would change; write nothing |
| `--force` | Let `add` overwrite an existing palette |
| `--append-missing` | (bash) Append palette keys that `colors.sh` doesn't have |
| `--porcelain` | Machine-readable output for `list` and `preview` |
| `-v, --verbose` | Extra detail on stderr |
| `-q, --quiet` | Suppress non-error output |
| `-h, --help` | Show usage |
| `-V, --version` | Print the version |

## How it works

A palette is a language-neutral TOML file. On `apply`, `stm` translates it into
whichever form your config actually uses.

### Lua configs → `colors_generated.lua`

`stm` writes a **new** file, `colors_generated.lua`, and **never touches your
`colors.lua`**. The generated file is a plain Lua module:

```lua
-- Generated by stm (sketchybar-theme-manager). DO NOT EDIT.
-- theme: tokyo-night
-- name: Tokyo Night

return {
  bar_bg = 0x001a1b26,
  bar_border = 0xff292e42,
  black = 0xff1a1b26,
  -- ...
}
```

Values are unquoted Lua number literals, which is what SketchyBar wants.

#### Two Lua shapes

Real configs consume colours in one of two shapes, and `stm` detects which one
your `colors.lua` uses.

**flat** — a single table of colours. This is the default, and what you get if
your config merges the generated table into your own defaults.

**nested** — `bar` and `popup` become sub-tables and a `with_alpha` helper is
included:

```lua
local with_alpha = function(color, alpha)
  if alpha > 1.0 or alpha < 0.0 then
    return color
  end
  return (color & 0x00ffffff) | (math.floor(alpha * 255.0) << 24)
end

return {
  black = 0xff1a1b26,
  transparent = 0x00000000,
  -- ...
  bar = { bg = 0x001a1b26, border = 0xff292e42 },
  popup = { bg = 0xc01f2335, border = 0xff565f89 },
  with_alpha = with_alpha,
}
```

You need `nested` if your `colors.lua` returns the generated table *wholesale*:

```lua
local ok, generated = pcall(require, "colors_generated")
if ok and generated then
  return generated          -- <- nothing of yours survives, so the generated
end                         --    table must be the complete shape
```

In that arrangement a flat table would make `colors.popup.bg` and
`colors.with_alpha` nil and the bar would fail to load. `stm` detects the shape
from the sub-tables in your own `colors.lua`; override with `--lua-dialect`.

`with_alpha` is emitted from a fixed, built-in definition inside `stm`. It is
never read from a palette — palettes carry data only, so installing someone
else's theme can change your colours and nothing else.

### Bash configs → in-place swap in `colors.sh`

`stm` rewrites the value of each `export NAME=0x...` line whose name matches a
palette key, and leaves everything else exactly as it found it — indentation,
`export` or not, single or double quotes, trailing comments, and any variables
of your own:

```diff
-export RED=0xffed8796            # accent red
+export RED=0xfff7768e            # accent red
-  export BG2=0xff363a4f          # indented on purpose
+  export BG2=0xff24283b          # indented on purpose
 export ICON_FONT="Hack Nerd Font:Bold:16.0"
```

Before the first edit it saves `colors.sh.stm-backup`, once. That backup always
holds your original file; switching themes later never overwrites it.

Both writers are atomic: the new content is written to a temp file in the same
directory and moved into place, so an interrupted run can't leave you with half
a config.

## Wiring `colors_generated.lua` into your config

This is the part worth reading carefully.

`stm` is **additive**. Your `colors.lua` stays yours and stays authoritative;
the generated file is an optional overlay. You wire the two together with a
`pcall`:

```lua
-- ~/.config/sketchybar/colors.lua

local defaults = {
  black = 0xff1a1b26,
  white = 0xffc0caf5,
  red = 0xfff7768e,
  green = 0xff9ece6a,
  blue = 0xff7aa2f7,
  yellow = 0xffe0af68,
  orange = 0xffff9e64,
  magenta = 0xffbb9af7,
  grey = 0xff565f89,
  bg1 = 0xff1f2335,
  bg2 = 0xff24283b,
  bar_bg = 0x001a1b26,
  bar_border = 0xff292e42,
  popup_bg = 0xc01f2335,
  popup_border = 0xff565f89,
}

-- If stm has written a generated palette, overlay it. If not, nothing happens.
local ok, generated = pcall(require, "colors_generated")
if ok and type(generated) == "table" then
  for k, v in pairs(generated) do
    defaults[k] = v
  end
end

return defaults
```

Then keep using `require("colors")` everywhere, exactly as before.

**Why `pcall` and a separate file, rather than rewriting `colors.lua`?**

- Your config works on a **fresh clone**, before `stm` has ever run. There is no
  generated file, `pcall` fails, your defaults are used. Nothing breaks.
- Your config works if you **delete `colors_generated.lua`**. That's the reset
  button: remove the file and you're back to your own palette.
- Your **defaults stay in version control** and the generated file doesn't. Your
  theme choice is machine-local state, not something you have to commit.
- `stm` never has to parse or modify hand-written Lua, so it can't mangle
  a config it doesn't fully understand.

Credit where it's due: this fallback pattern was inspired by the mechanism in
[NoamFav/sketchybar](https://github.com/NoamFav/sketchybar).

`stm init` prints this snippet for you when it detects a Lua config.

### SbarLua

The generated file is an ordinary Lua module returning a table, so it works
directly under [SbarLua](https://github.com/FelixKratz/SbarLua):

```lua
local colors = require("colors_generated")
sbar.bar({ color = colors.bar_bg })
```

## Bringing your own theme, or your whole dotfiles

`stm` does not require your config to look like anyone else's. Three things,
all plain files in your own tree, cover the gap:

**A palette** says what the colours are. **`[mapping]`** says what *you* call
them. **A template** says how they should be written out. You need the first
one; the other two only when your config's shape differs from the built-in
writers.

### Start from what you already have

```sh
stm import                       # reads your colors.lua or colors.sh
stm doctor                       # what resolves, what doesn't
stm apply imported
```

`import` reads your existing colours file and writes a palette from it. Lua
nesting is flattened (`bar.bg` becomes `bar_bg`), and in a `colors.sh`
reference lines like `export ITEM_BG_COLOR=$SURFACE0` are resolved so the
palette carries real values. Anything it cannot read — a function, a
non-colour — is listed rather than dropped quietly.

If your config names its colours its own way, it may have none of the fifteen
canonical keys. Inherit them:

```sh
stm import --slug mine --base tokyo-night
```

`stm export <theme>` is the reverse, and round-trips exactly — that is how you
turn a config you like into a palette worth sharing.

### Inheriting

```toml
name = "Gruvbox Red"
slug = "gruvbox-red"
base = "gruvbox"

[colors]
red = "#ff0000"
```

Everything not named here comes from `gruvbox`. Chains are allowed; cycles,
self-inheritance and chains deeper than eight are refused.

### Renaming — `[mapping]`

```toml
[mapping]
gray = "grey"              # my config says gray; the canonical key is grey
brand = "#ff0000"          # my config says brand; pin it to a literal
```

The left side is the name your config and templates use. The right side is
either a canonical key or a literal colour. An unresolvable right side is an
error, not a silent skip.

`[mapping]` is applied *after* a palette is validated, so it can rename keys
for your config but cannot supply keys a palette is missing. Use `base =` for
that.

### Templates

When neither built-in writer matches your layout, write the file yourself and
let `stm` fill in the colours. Drop `stm/templates/lua.tpl` or
`stm/templates/bash.tpl` into your config dir and it replaces the built-in
writer entirely.

```lua
-- {{name}} ({{slug}}), generated {{generated}}
{{with_alpha}}

return {
{{colors_lua}}
{{children_lua}}
  with_alpha = with_alpha,
}
```

| Placeholder | Expands to |
| --- | --- |
| `{{<key>}}` | any colour, after `[mapping]` |
| `{{name}}` `{{slug}}` `{{variant_label}}` `{{generated}}` | metadata |
| `{{colors_lua}}` / `{{colors_bash}}` | every colour, as Lua fields or `export` lines |
| `{{extras_lua}}` / `{{extras_bash}}` | the same, `[extras]` only |
| `{{children_lua}}` | the `bar` / `popup` sub-tables |
| `{{with_alpha}}` | stm's built-in helper |

Only `{{identifier}}` with a lower-case identifier substitutes. Anything else
after `{{` is literal text, so a real Lua constructor like `{{1,2},{3,4}}`
passes through untouched. Write `{{{{` for a literal `{{`. An unrecognised
identifier is a hard error — a half-substituted config is worse than none.

A template is yours and is trusted: it may contain whatever Lua or shell you
like. A palette is not trusted, and the only thing it contributes to a render
is a value already validated as eight hex digits. `stm` never installs a
template from a palette or fetches one from the network.

### Proving it didn't touch anything else

```console
$ stm verify
OK — 69 files unchanged; stm touched only what it owns
```

Each `apply` records a checksum of every file in your config dir that `stm`
does not own. `verify` re-checks them and reports anything changed, added or
removed. That is the non-destructiveness promise made checkable rather than
merely stated. `--no-manifest` turns it off.

### Config formats

| Detected | Behaviour |
| --- | --- |
| `colors.lua` or any `.lua` | writes `colors_generated.lua` |
| `colors.sh` | rewrites value lines in place |
| `config.sh` and nothing else | writes `config-examples/<theme>.sh` and prints the `source` line to add |

The third is for configs built around sourcing a snippet. Nothing existing is
modified at all — you point one `source` line at the generated file.

## Configuration

`stm.config.toml` is optional — the defaults are usually right.

```toml
sketchybar_dir = "~/.config/sketchybar"
format = "auto"          # auto | lua | bash | config-sh
lua_dialect = "auto"     # auto | flat | nested
palette_dir = "~/.config/sketchybar/palettes"
default_theme = "tokyo-night"

[output]
lua = "colors_generated.lua"     # a bare filename, inside the config dir
bash = "colors.sh"
template_dir = "stm/templates"

[mapping]
gray = "grey"

[notes]
tokyo-night = "Matches my Ghostty theme"
```

`[output]` values are bare filenames and are validated as strictly as a theme
name: no paths, no leading dot, restricted charset, and `stm` refuses to be
pointed at your own `colors.lua` or at its own state files.

**Where `stm` looks for it**, first match wins:

1. `--config <path>`
2. `$STM_CONFIG`
3. `./stm.config.toml`
4. `$XDG_CONFIG_HOME/stm/stm.config.toml` (or `~/.config/stm/stm.config.toml`)

**How the SketchyBar directory is resolved**, first match wins:

1. `--dir <path>`
2. `$SKETCHYBAR_CONFIG_DIR`
3. `sketchybar_dir` from the config file
4. `$XDG_CONFIG_HOME/sketchybar`, else `~/.config/sketchybar`

**Where palettes are searched**, in order — the first directory that has a
given slug wins, so your own palettes shadow the bundled ones:

1. `--palette-dir <path>` (when given, it is the only user directory consulted)
2. `$STM_PALETTE_DIR`
3. `palette_dir` from the config file
4. `<sketchybar_dir>/palettes`
5. the palettes bundled with `stm`

**How the format is decided**, first match wins:

1. `--format lua|bash`
2. `$STM_FORMAT`
3. `format` from the config file, when it isn't `auto`
4. auto-detection: a `colors.lua`, a `colors_generated.lua`, or any `.lua` file
   means `lua`; a `colors.sh` means `bash`

If a directory contains **both** a Lua file and a `colors.sh`, `stm` refuses to
guess and asks you to pass `--format`. Both writers modify files; guessing wrong
is worse than stopping.

Config values are read as literal strings. A leading `~` expands to your home
directory; nothing else is expanded, and the file is never sourced.

## Palette format

```toml
name = "Tokyo Night"
slug = "tokyo-night"
variant_label = "Tokyo Night"

[colors]
black = "0xff1a1b26"
white = "0xffc0caf5"
# ...
```

The file name must match the `slug`.

**Required colour keys** — all fifteen, in every palette:

`black` · `white` · `red` · `green` · `blue` · `yellow` · `orange` · `magenta` ·
`grey` · `bg1` · `bg2` · `bar_bg` · `bar_border` · `popup_bg` · `popup_border`

`transparent` is added automatically as `0x00000000` if a palette does not
declare it, because several real configs reference `colors.transparent`
unguarded. A palette may still override it.

Extra keys beyond these are allowed and are passed straight through to the
output, so you can carry your own `my_accent` if your config uses one.

### The bash Catppuccin dialect

Many shell-based configs name their colours with Catppuccin's 26-colour
vocabulary (`ROSEWATER`, `MAUVE`, `SURFACE0`, `CRUST`, …) rather than
`BLACK`/`WHITE`. Every bundled palette therefore also carries those keys, with
values taken from [AwesomeAdil/dotfiles](https://github.com/AwesomeAdil/dotfiles),
so a `colors.sh` written that way is themed correctly with no configuration.

Reference lines are left alone. Only literal `0x` values are rewritten, so a
line like `export ITEM_BG_COLOR=$SURFACE0` keeps pointing at whatever
`SURFACE0` now holds.

### Checking your config

```console
$ stm doctor
...
Key coverage (config vs palette "tokyo-night")
  used and provided        bg1 bg2 black blue green grey ...
  used but missing         (none)
  provided but unused      bar_bg bar_border
```

`doctor` reports the detected format and Lua dialect, then compares the colour
keys your config actually consumes against the ones the palette provides. In a
Lua config a missing key is an error — it resolves to `nil` and breaks the bar.
In a shell config it is only informational, since the variable keeps whatever
value it already had.

**Values** are `0xAARRGGBB` — exactly eight hex digits, alpha first — or
`#RRGGBB`, which is taken as fully opaque. `#rgb` and `#aarrggbb` are refused
rather than guessed at. `0xAARRGGBB` is SketchyBar's own colour format. `bar_bg` is usually given a `00` alpha for a
transparent bar; popups typically use `c0`.

Palettes are parsed by a deliberately small TOML reader: top-level strings, one
`[colors]` table, `key = "value"` and comments. Arrays, nested tables, multi-line
strings and unquoted values are rejected rather than ignored, so a typo is an
error instead of a silently missing colour.

## Adding your own theme

Write a `.toml` with the fifteen required keys, then:

```sh
stm add my-theme ./my-theme.toml
stm apply my-theme
```

Or just drop the file into your palette directory. A user palette with the same
slug as a bundled one shadows it, so you can override `nord` with your own
version without deleting anything.

| Code | Meaning |
| --- | --- |
| `0` | Success |
| `1` | Invalid palette |
| `2` | Config directory or format could not be resolved |
| `3` | Theme not found |
| `4` | Refusing to overwrite (pass `--force`) |
| `64` | Usage error |

## Requirements

- macOS (SketchyBar is macOS-only)
- bash 3.2 or newer — the `/bin/bash` that ships with macOS is fine
- [SketchyBar](https://github.com/FelixKratz/SketchyBar), for the `--reload`

No Node, no Python, no Lua, no external dependencies. `stm` never touches the
network.

## Development

```sh
tests/run.sh                                    # against /bin/bash (3.2)
STM_BASH="$(brew --prefix)/bin/bash" tests/run.sh   # against bash 5.x
tests/run.sh test_apply_bash.sh                 # a single file

shellcheck -s bash bin/stm tests/*.sh
shellcheck -s sh install.sh
```

Every test runs in a `mktemp -d` sandbox with `HOME` redirected inside it, so
the suite can never touch your real `~/.config/sketchybar`.
